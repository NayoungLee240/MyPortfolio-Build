DESIGN 01인증

요청마다 토큰을 바꿔 탈취와 중복 로그인을 막았습니다

요청 한 번의 흐름
  1. 클라이언트가 현재 토큰으로 API 요청
  2. 서버가 Redis의 최신 토큰과 대조
  3. 새 토큰 발급, Redis의 최신 토큰 교체
  4. 이전 토큰은 즉시 폐기
✕ 문제

유효기간이 긴 토큰은 탈취되면 만료 전까지 막을 수 없습니다. 같은 계정으로 여러 기기에서 동시에 접속하는 것도 막아야 했습니다.

→ 결정

Refresh Token 하나로 인증을 단순화하고, 요청마다 토큰을 교체해 Redis에는 계정별 최신 토큰 하나만 유효하게 저장했습니다. 동시 요청이 들어오면 기존 토큰을 폐기하고 최신 토큰만 남깁니다.

✓ 결과

탈취된 토큰은 다음 요청 한 번이면 쓸 수 없게 되고, 새 로그인이 들어오면 기존 세션이 바로 끊겨 중복 로그인이 차단됩니다. Firebase(iOS, Android), Steam, EroLabs 로그인도 같은 흐름으로 묶었습니다.

DESIGN 02접속 대기열

서버가 다운된 날, 대기열 서버를 긴급 투입했습니다

동접이 서버 한도를 넘어 서버가 다운되자, 초과 인원을 줄 세워 차례로 들여보내는 대기열 서버와 Delay Redis를 따로 만들어 붙였습니다.

동작 흐름
  1. 접속 요청이 대기열 서버로 먼저 들어옴
  2. Delay Redis로 현재 동접 확인
  3. 한도를 넘으면 대기 순번 발급

DESIGN 03무중단 스키마 변경

서비스를 멈추지 않고 핵심 테이블 키를 바꿨습니다

업적, 에스퍼 등 핵심 테이블의 키 구조를 바꿔야 했지만, 한 번에 일괄 변환하면 라이브 중 DB 부하가 순간적으로 치솟습니다.

진행 방식
  1. 정기점검 때 새 코드를 먼저 배포
  2. 유저가 로그인하면 그 유저의 데이터만 변환
  3. 이후 정기점검마다 남은 데이터를 조금씩 변환
  4. 전체 전환 완료
비교한 번에 일괄 변환지연 + 분할 변환 (선택)
DB 부하변환 순간에 급증로그인 트래픽과 점검 시간에 분산
서비스 영향긴 점검이 필요할 수 있음서비스 중단 없음
접속하지 않는 유저함께 처리정기점검 때 나눠서 처리
왜 바꿨나

기존 키 구조로는 조회 효율이 떨어졌습니다. 업적, 에스퍼처럼 자주 조회되는 테이블이라 그대로 둘 수 없었습니다.

느린 쿼리와 재화 정합성은 DB에서 해결했습니다

느린 쿼리 찾아 고치기
  1. Slow Query Log로 느린 쿼리 수집
  2. EXPLAIN으로 실행 계획 확인
  3. 인덱스가 빠진 쿼리를 찾아 인덱스 추가
재화 처리 프로시저

현재 재화 확인, 재화 지급, 로그 기록을 하나의 DB 프로시저로 묶었습니다. 재화가 바뀔 때마다 로그가 반드시 남아, 비정상적인 재화 변동을 추적할 수 있습니다.

Redis와 DB 역할 분리
  • 세션과 호출이 많은 유저 데이터를 Redis에 저장해 DB 호출 최소화
  • 임시 데이터는 TTL로 만료
  • 재화 같은 민감 데이터는 DB에서 처리
읽기 성능은 Redis로, 재화처럼 중요한 데이터는 DB에서 처리합니다.

서버를 늘렸더니 DB 커넥션이 먼저 터졌습니다

예상보다 많은 유저가 몰려 PM2 Cluster 인스턴스를 급히 늘리자, 프로세스마다 DB에 직접 연결하던 구조 탓에 커넥션 수가 함께 치솟았습니다.

발생
INCIDENT
동접에 맞춰 Cluster 인스턴스를 늘리자 DB 쿼리 오류가 나기 시작
원인
ROOT CAUSE
인스턴스 수만큼 DB 커넥션이 늘어나는 것을 모니터링으로 확인
대응
RESPONSE
조사부터 적용까지 3–5일. 바로 다음 점검에 RDS Proxy를 붙여 커넥션 풀을 한곳에서 관리
결과
RESULT
쿼리 오류 해소. 이후 인스턴스를 늘려도 DB 연결 수가 안정적으로 유지
이 경험으로 바뀐 것

커넥션 관리가 얼마나 중요한지 확실히 깨달았습니다. 이제는 서버를 늘리기 전에 인스턴스 수와 커넥션 풀 크기로 DB 연결 상한을 먼저 계산하고, 쿼리 효율도 함께 따져 봅니다.
